# Orbit chat quality eval

How good Orbit's chat agent is on the six benchmark prompts, judged by a rubric (gpt-6.1-sol via AiClient.json). Generated by
`pnpm --filter @brandloop/agent eval` (packages/agent/eval); the block between the markers is rewritten on each run.

## Method

- **Fixture.** An invented user, Maya Okafor, fractional CTO at "Northbeam Labs" (Lisbon): identity/about, story and personal memory,
  writing rules (British spelling, no hashtags or emojis, banned words, ending rule), voice memory, a full strategy (goal, positioning,
  three weekly series: Scope Clinic Mon, Build Notes Wed, Hiring Desk Fri), two knowledge items (MVP vs POC workshop notes with a real
  client case and numbers; a first-engineer hiring checklist), embedded like the app's ingest, and an own writing style selected on the profile.
- **Chats.** (a)+(b) in one chat; (c)+(d) in one chat with the post open (documentContext, as the side panel sends); (e) alone; (f) alone,
  pasting the post (c) produced. Every turn goes through `runChatTurn` with the real orchestrator (gpt-6.1-sol), specialists and embedder.
  No web search, no title calls, never Deepgram. The eval user is deleted afterwards and every table is checked for leftover rows (0 every run).
- **Judge.** gpt-6.1-sol via `AiClient.json` with a zod schema, six dimensions scored 1–5 (null when not applicable), calibrated so generic
  AI output is a 3. It sees the fixture, today's date, the chat so far, the tool trace, the post before/after and the reply.
  `--rejudge <n>` re-scores a saved run, so runs 1 and 2 were re-scored with the final judge and every column uses the same judge.

## What changed between runs

- **Run 1** (baseline, knowledge chunks without embeddings) and **run 2** (baseline with embeddings, as production): drafts used a
  hypothetical example instead of the user's real workshop case, the orchestrator read memory before every draft although the writer
  already gets the grounding, hook variations were saved as a post document (spending the chat's one post), draft feedback used no
  tools, the edit reply quoted a made-up word count, and the orchestrator called itself Brandloop.
- **Run 3** after `fix(agent): prompt quality from eval run 2`: knowledge base searched before ideas, drafts and feedback, with the facts
  passed in the brief; no memory reads just to draft; options returned in chat; feedback grounded in rules and knowledge with quoted lines
  and rewrites; no guessed counts; writer builds on the user's real material and writes options on request; Orbit naming.
  (A first attempt at run 3 was aborted after two prompts because a concurrent unit-test run deleted the shared eval user; the harness
  now isolates test identities. Its files are kept as `orbit-run-3-aborted.*` and excluded from the tables.)
- **Run 4** after `fix(agent): prompt quality from eval run 3`: no readKB after a full searchKB result, posted text without em dashes or
  stretched claims, advisor/client roles kept accurate. Overall flat (4.79 → 4.76, within single-sample noise); instruction following and
  grounding reached 5.00, but (b) regressed in speed and variety (see gaps).

## Remaining gaps

- **Post ideas (b).** In run 4 the orchestrator routed ideas through the writing specialist (the "short options" rule caught them):
  70 s instead of 19 s, and three of five ideas reused the same client case. Ideas should be written by the orchestrator (or a
  content-planning specialist, which exists in prompts but has no tool yet) and should vary their source material.
- **Jargon for the audience.** Hooks still use unexplained terms (frontend, deploys) for non-technical founders.
- **Draft feedback (f)** sometimes elevates a debatable precision point to a top-three fix.
- **Memory recap (a)** omits the strategy and voice.
- **Latency.** Drafts take 35–40 s (searchKB + writer + createDocument).
- **Missing UI affordances.** Hook variations, draft analysis and idea pickers are covered in text, which the judge liked, but
  the picker cards are missing in these runs.

## Latest run (6): failures the judge found

- (b) [voice] "Opening line to start from: What should be settled before you interview engineer number one?" — This is a rhetorical-question opening, which Maya’s writing rules explicitly prohibit.
- (b) [tools] "1. generateIdeas [ok] input={"count":5}" — The trace shows idea generation without first reading the strategy, despite the request being explicitly based on it.
- (d) [instruction] "Post updated by this turn (v2, 127 words):" — The requested limit was under 120 words, but the updated post is 127 words.
- (d) [tools] "Server checks on the post: length ok" — The length check is inconsistent with the supplied post, which is identified as 127 words and therefore exceeds the under-120-word request.
- (e) [instruction] "The three hook variations are ready: a bold claim, a prediction, and a how-to." — This describes the requested deliverable instead of giving the three hook variations.
- (e) [memory] "The three hook variations are ready: a bold claim, a prediction, and a how-to." — The reply misses the chance to use Maya’s specific first-hire guidance, especially scoping the first 90 days and hiring for range.
- (f) [craft] "spell out “proof of concept” and “minimum viable product” in the opening for readers unfamiliar with the acronyms." — This is a reasonable edit, but the reply misses a more substantive fix: “meaningful next step” is vague, while the example and source notes make the MVP test specifically about whether customers will use and pay.
- (f) [instruction] "The analysis card is ready." — The reply says an analysis card is ready but does not provide one; it only gives two short recommendations.
